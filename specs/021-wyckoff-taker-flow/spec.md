# Feature Specification: Taker Buy/Sell Flow as a Wyckoff Refinement

**Feature Branch**: `main` (Spec Kit feature directory: `specs/021-wyckoff-taker-flow`)

**Created**: 2026-09-28

**Status**: Draft

**Input**: `specs/020-orderflow-and-social-data-research/research.md` item #1 (top priority, zero
cost): Binance's raw klines endpoint (`publicGetKlines`, verified directly) returns
`taker_buy_base_volume` per candle — the volume within that candle generated by aggressive
(market/taker) buy orders, vs. the rest generated by aggressive sells. CCXT's unified `fetch_ohlcv`
discards this. Slice 017 validated "high volume at the break" without knowing *which side* generated
it; this slice tests whether knowing that side sharpens the edge further.

## Two competing hypotheses, both pre-declared (no p-hacking after seeing results)

Wyckoff theory supports two plausible mechanics for the same Spring/Upthrust pattern, so both are
tested honestly rather than picking one after seeing which fits:

1. **Absorption hypothesis**: a Spring breaks support on volume dominated by aggressive SELLING
   (taker_buy_ratio low) that gets absorbed rather than driving price further down — classic Wyckoff
   "supply meets demand" at a shakeout. Mirror for Upthrust: aggressive BUYING absorbed by hidden
   supply. Predicts: for hot events, low taker_buy_ratio at the break is the confirming signature;
   for cold events, high taker_buy_ratio.
2. **Aggressive-entry hypothesis**: the reversal is driven by aggressive buyers already stepping in
   during the breakdown candle itself (for Spring), or aggressive sellers during the breakout (for
   Upthrust). Predicts the opposite alignment: taker_buy_ratio matching the eventual direction.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Does either taker-flow hypothesis sharpen the already-validated edge? (Priority: P1)

**Independent Test**: Reuse slice 017's 330 confirmed extreme-volume events. Refetch the same 4h
OHLCV via Binance's raw klines (not CCXT's unified wrapper) to recover `taker_buy_base_volume`,
compute `taker_buy_ratio` at each event's break candle, and evaluate both hypotheses with the same
chronological 70/30 in-sample/out-of-sample split and lift-over-baseline framing as slices 017/019.

**Acceptance Scenarios**:

1. **Given** the event set, **When** `taker_buy_ratio` is computed at the break candle for each,
   **Then** both the absorption-hypothesis bucket and the aggressive-entry-hypothesis bucket are
   evaluated in-sample and out-of-sample, reported regardless of outcome (FR-003 discipline, same as
   slices 017/019).
2. **Given** results, **When** the report concludes, **Then** it states which hypothesis (if either)
   held up, combined with the still-pending operator decision from slices 017-019.

### Edge Cases

- Binance's raw klines response shape must be parsed defensively (numeric strings, 12-column array)
  — malformed/missing fields degrade that candle's `taker_buy_ratio` to `NaN`, excluded from
  aggregation, not treated as 0 or 0.5.
- Same MIN_SAMPLE=30 / actionable-bar (out-of-sample win rate ≥60%, p<0.05) as slices 017/019.

## Requirements *(mandatory)*

- **FR-001**: MUST use Binance's raw klines response (verified format: index 9 = taker buy base
  volume, index 5 = total volume) — not a reimplementation or estimate.
- **FR-002**: MUST reuse slice 017's exact 330-event population (same detection, same horizon) —
  this is a refinement test, not a new event search.
- **FR-003**: MUST evaluate both pre-declared hypotheses with the same in-sample/out-of-sample
  discipline as slices 017/019, reporting both regardless of outcome.
- **FR-004**: MUST NOT wire anything into `SignalEnhancer`/`notify_all` — same Principle III
  discipline as every prior validation slice.

## Success Criteria *(mandatory)*

- **SC-001**: Both hypotheses evaluated in-sample/out-of-sample with concrete numbers.
- **SC-002**: One clear recommendation combined with the still-pending slices 017-019 decision.
- **SC-003**: Existing test suite unaffected (research artifact).
